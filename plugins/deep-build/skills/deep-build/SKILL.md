# 딥 빌드 (1단계: 설계 → 계획 → 검토)

딥 인터뷰가 "무엇을, 왜"를 정했다면, 여기서는 "어떻게"를 정한다. 스펙을 보고 설계 문서를 쓰고, 설계를 보고 작업 목록을 만들고, 계획을 쓰지 않은 검토자가 스펙과 대조한다. 사람 승인은 없다. 그래서 두 가지가 대신 지킨다: **코드**가 연결 누락을 잡고, **검토 에이전트**가 내용을 본다.

이 단계는 검토 통과(`planned`)에서 끝난다. 구현 단계는 아직 없다.

## 상태 명령

`BD <명령>`은 아래를 줄인 것이다. Bash에서는 **항상 전체를 그대로** 쓴다.

```
node "${CLAUDE_SKILL_DIR}/scripts/build.mjs" <명령> --session ${CLAUDE_SESSION_ID} [플래그]
```

| 명령 | 언제 |
|:---|:---|
| `start --spec <경로> [--force]` | 시작. 스펙을 해석해 고정 항목 ID와 완료 기준 ID(AC-1…)를 돌려준다 |
| `design --file <경로>` | 설계 문서를 쓴 뒤 등록. 4개 절 검사 |
| `plan --input @<경로>` | 작업 목록 JSON을 등록. 연결 검사 뒤 계획 파일을 코드가 쓴다 |
| `review --input @<경로>` | 검토 에이전트의 JSON 판정을 기록 |
| `status` | 현재 상태, 이어하기 |

- 결과는 JSON. `"ok": false`면 `error`를 해결한다. 우회하지 않는다.
- JSON 입력은 Write 도구로 프로젝트 밖 임시 폴더(`$TMPDIR`)에 쓰고 `@경로`로 넘긴다.
- `.deep-interview/plans/`와 `.deep-interview/builds/`는 직접 쓰지 않는다 (훅이 막는다). 설계 문서(`.deep-interview/designs/`)는 직접 쓴다.

## 흐름

### 1. 시작

인자로 받은 스펙 경로로 `BD start --spec <경로>`를 실행한다.

- 결과의 `fixed_items`(고정 항목 ID)와 `criteria`(AC-1, AC-2… 와 문장)를 메모한다. 계획의 모든 작업은 이 ID들로 스펙과 연결된다.
- 오류에 "조기 종료된 스펙"이 나오면: 딥 인터뷰가 이미 사용자에게 물어봤고 진행하기로 한 경우에만 `--force`를 붙인다. 직접 불렸다면 스펙의 "남은 질문"과 미달 사실을 보여주고 AskUserQuestion으로 "그래도 진행할까요?"를 한 번 묻는다.
- 스펙 전체를 읽는다. 특히 **지킬 조건, 하지 않을 것, 다 됐다는 기준, 남은 질문, 코드에서 확인한 것**.
- 기존 코드가 있으면 스펙의 "코드에서 확인한 것"에 적힌 파일을 Read/Grep으로 다시 본다.

시작을 알린다:

> 딥 빌드 시작: {스펙 제목}
> 고정 항목 {n}개, 완료 기준 {n}개. 설계 → 계획 → 검토 순서로 진행하고, 검토가 통과하면 멈춥니다.

### 2. 설계 문서

`.deep-interview/designs/<slug>.md`를 Write로 쓴다. 네 절이 **모두** 있어야 하고, 각 절은 내용이 있거나 "생략: <이유>" 한 줄이 있어야 한다. 이 스펙에 해당하는 것만 쓰고 억지로 채우지 않는다.

```markdown
# {제목} — 설계

- 스펙: {경로}

## 시퀀스
{주요 흐름 1~3개를 Mermaid sequenceDiagram으로. 누가 누구를 부르고 무엇이 돌아오는지}
또는
생략: {이유 한 줄. 예: 호출 주체가 하나뿐이라 흐름이 자명함}

## 상태
{상태가 바뀌는 대상이 있으면 Mermaid stateDiagram-v2. 예: 신청 → 대기 → 승인/반려}
또는 생략: {이유}

## ERD
{저장하는 데이터가 있으면 Mermaid erDiagram. 엔티티·필드·관계}
또는 생략: {이유}

## API
{외부에 노출하는 엔드포인트·명령·함수가 있으면 표: | 이름 | 입력 | 출력 | 오류 |}
또는 생략: {이유}

## 설계 메모
{스펙의 "남은 질문" 중 설계에서 답이 정해진 것, 선택한 구조와 이유}
```

쓴 뒤 `BD design --file .deep-interview/designs/<slug>.md`로 등록한다. 거부되면 빠진 절을 채운다.

### 3. 계획

설계를 보고 작업 목록을 만든다. 작업은 **그 자체로 테스트할 수 있는 가장 작은 단위**다. superpowers 계획 형식을 따른다: 작업마다 고칠 파일, 인터페이스, 먼저 실패할 테스트.

규칙:
- 스펙의 **모든 고정 항목 ID와 모든 완료 기준 ID**에 담당 작업이 하나 이상 있어야 한다. 없으면 코드가 거부한다.
- `files`는 실제 경로. 새 파일이면 만들 경로.
- `interface`는 이름·시그니처·입출력. "적절히 처리"처럼 추측이 필요한 말은 쓰지 않는다.
- `test`는 작업 전에 실패하고 작업 뒤에 통과할 테스트를 한 문장으로.
- `depends_on`으로 순서를 적는다. 작업 수가 3개 이하인지 4개 이상인지는 다음 단계(구현)가 방식을 고르는 기준이 된다.
- 스펙의 "하지 않을 것"에 해당하는 작업을 넣지 않는다.

JSON을 임시 파일에 쓰고 `BD plan --input @<경로>`를 실행한다.

```json
{
  "tasks": [
    {
      "id": "T1",
      "title": "휴가 신청 저장",
      "files": ["src/leave/request.ts", "src/leave/request.test.ts"],
      "interface": "createRequest({employeeId, start, end, type}) → {id, status:'pending'}; 과거 날짜·초과 일수면 Error",
      "test": "어제 날짜로 신청하면 Error, 오늘 날짜 반차면 status pending",
      "covers": { "fixed": ["화면:신청폼"], "criteria": ["AC-1", "AC-6"] },
      "depends_on": [],
      "notes": "초과 검사는 T3의 잔여 계산을 쓴다"
    }
  ]
}
```

통과하면 코드가 `.deep-interview/plans/<slug>.md`를 쓴다(작업 목록, 상세, 연결 표). 거부되면 빠진 ID나 빈 필드를 채운다.

### 4. 검토

계획을 쓰지 않은 **새 에이전트 한 명**에게 검토를 맡긴다. Agent 도구로 `subagent_type: "general-purpose"`를 띄우고, 프롬프트에 이 폴더의 `reviewer.md` 전문과 스펙·설계·계획 경로를 넣는다. 읽기만 하고 파일을 고치지 말라고 명시한다. 2회차부터는 직전 지적과 무엇을 고쳤는지도 넣는다.

에이전트가 돌려준 JSON을 임시 파일에 쓰고 `BD review --input @<경로>`로 기록한다.

| 결과 | 할 일 |
|:---|:---|
| `pass` → 상태 `planned` | 5. 멈춤으로 |
| `revise` → 상태 `revising` | blocker 지적을 설계(2)나 계획(3)에 반영하고 다시 등록 → 다시 검토. 최대 3회 |
| 3회 뒤에도 `revise` → 상태 `stuck` | 구현하지 않는다. 남은 지적을 표로 보여주고 멈춘다 |

검토자의 지적에 동의하지 않을 수 있다. 그래도 근거 없이 넘기지 않는다: 반박이면 왜 스펙에 맞는지 다음 검토 프롬프트에 적고, 검토자가 다시 판단하게 한다.

### 5. 멈춤

`planned`가 되면 아래만 보여주고 멈춘다. 구현 단계는 다음에 만들 예정이다.

- 설계 문서 경로, 계획 경로
- 작업 수와 순서(id·제목만)
- 검토 횟수와 마지막 판정 요약
- "구현 단계는 아직 없습니다. 계획대로 구현하려면 '이 계획으로 구현해줘'라고 말씀해 주세요."

`stuck`이면: 설계·계획 경로, 남은 blocker 지적 표, "사용자가 정해야 넘어갈 수 있는 것"을 보여주고 멈춘다.

## 지키는 규칙

1. **스펙이 기준이다.** 설계와 계획이 스펙과 충돌하면 스펙을 따른다. 스펙이 틀렸다고 생각되면 고치지 말고 "설계 메모"에 적고 사용자에게 알린다.
2. **이 단계에서는 소스 코드를 고치지 않는다.** 쓰는 파일은 설계 문서뿐이고, 계획은 코드가 쓴다.
3. **숫자·연결은 코드가 본다.** 고정 항목·완료 기준 연결, 검토 횟수는 `build.mjs`가 센다. 직접 세지 않는다.
4. **검토자는 새 에이전트다.** 이 세션이 스스로 검토하지 않는다.
5. **글은 사용자의 CLAUDE.md 규칙**을 따른다: 한국어, 결론 먼저, 표, 짧은 문장.

## 이어하기

`BD status`로 상태를 본다. `designing`이면 2부터, `planning`이면 3부터, `reviewing`이면 4부터, `revising`이면 마지막 지적을 보고 2 또는 3부터, `planned`/`stuck`이면 5를 다시 보여준다.
