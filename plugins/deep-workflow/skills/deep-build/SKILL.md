# 딥 빌드

딥 인터뷰가 "무엇을, 왜"를 정했다면, 여기서는 "어떻게"를 정하고 실제로 만든다. 사람 승인은 없다. 그래서 두 가지가 대신 지킨다: **코드**가 연결 누락·테스트 통과·증거를 검사하고, **새 에이전트**가 내용을 본다.

| 단계 | 끝나는 조건 | 상태 |
|:---|:---|:---|
| 설계 → 계획 → 검토 | 검토 에이전트 `pass` (최대 3회) | `planned` |
| 구현 | 모든 작업의 테스트가 코드 실행으로 통과 (작업마다 최대 3회) | `executing` |
| 완료 판정 | 완료 기준마다 증거 명령 통과 + 최종 리뷰 `pass` | `done` |

어느 단계든 한계를 넘으면 `stuck`으로 멈추고 사용자에게 보여준다.

## 상태 명령

`BD <명령>`은 아래를 줄인 것이다. Bash에서는 **항상 전체를 그대로** 쓴다.

```
node "${CLAUDE_SKILL_DIR}/scripts/build.mjs" <명령> --session ${CLAUDE_SESSION_ID} [플래그]
```

| 명령 | 언제 |
|:---|:---|
| `start --spec <경로> [--force] [--restart]` | 시작. 스펙을 해석해 고정 항목 ID와 완료 기준 ID(AC-1…)를 돌려준다. 인터뷰 기록이 있으면 빠진 고정 항목·조기 종료를 대조한다 |
| `design --file <경로>` | 설계 문서를 쓴 뒤 등록. 4개 절 검사. 검토 통과 전에는 언제든 다시 등록할 수 있다 |
| `plan --input @<경로>` | 작업 목록(테스트 명령 포함)과 완료 기준별 증거 명령을 등록. 연결·순환 검사 뒤 계획 파일을 코드가 쓴다 |
| `review --input @<경로>` | 검토 에이전트의 JSON 판정을 기록 |
| `execute` | 구현 시작. 작업 수로 방식을 정하고 순서를 돌려준다 |
| `task-done --task <id>` | 계획에 고정된 그 작업의 테스트 명령을 코드가 실행. 종료 코드 0이어야 완료 |
| `task-review --task <id> --input @<경로>` | 에이전트 방식에서 리뷰 판정 기록 |
| `reopen --task <id>` | 끝난 작업을 (의존 작업까지) 다시 연다. verify 실패나 최종 리뷰 revise 뒤 작업을 고칠 때 |
| `amend --input @<경로>` | 구현 중에 계획의 테스트·증거 명령만 고친다 (경로 오타 등). 고친 작업은 다시 열린다 |
| `verify [--criterion <AC id>]` | 계획에 고정된 완료 기준별 증거 명령을 코드가 실행. 3회 실패면 stuck |
| `final-review --input @<경로>` | 최종 리뷰 판정 기록. AC별 판정이 모두 있어야 한다 |
| `status` | 현재 상태, 이어하기 |

- 결과는 JSON. `"ok": false`면 `error`를 해결한다. 우회하지 않는다. `"ok": true`여도 **`passed: false`나 `status: "stuck"`이면 실패**다(종료 코드 2). `passed`·`task_status`·`status`를 읽는다.
- JSON 입력은 Write 도구로 프로젝트 밖 임시 폴더에 쓰고 `@경로`로 넘긴다. 경로는 `/tmp/deep-build-${CLAUDE_SESSION_ID}/<이름>.json`처럼 절대 경로로 쓴다(Write는 `$TMPDIR`을 풀지 않는다).
- `task-done`·`verify`는 Bash 도구의 `timeout`을 600000(10분)으로 준다. 명령 하나는 코드가 8분에서 끊는다. 증거 명령이 여럿이고 길면 `verify --criterion AC-1`처럼 하나씩 실행한다. 그래도 넘칠 것 같으면 Bash `run_in_background`로 실행하고 결과를 기다린다.
- `.deep-interview/sessions/`, `plans/`, `builds/`는 직접 쓰지 않는다 (훅이 막는다). 설계 문서(`.deep-interview/designs/`)는 직접 쓰되, 등록한 뒤에 바꾸면 `execute`가 거부하고 다시 등록·검토해야 한다.

## 흐름

### 1. 시작

먼저 `BD status`를 본다. 이 세션에 빌드가 이미 있으면(`exists: true`) "이어하기"를 따른다. `done`/`stuck`이면 8절을 다시 보여주고 멈춘다. 새로 하려면 사용자가 그렇게 말했을 때만 `--restart`.

없으면 인자로 받은 스펙 경로로 `BD start --spec <경로>`를 실행한다. 인자에 `--force`가 붙어 있으면(딥 인터뷰가 조기 종료 스펙을 넘긴 경우) 그대로 붙인다.

- 결과의 `fixed_items`(고정 항목 ID)와 `criteria`(AC-1, AC-2… 와 문장)를 메모한다. 계획의 모든 작업은 이 ID들로 스펙과 연결된다. `warnings`가 있으면 사용자에게 한 줄 보여준다.
- 오류에 "조기 종료된 스펙"이 나오면: 딥 인터뷰가 이미 사용자에게 물어봤고 진행하기로 한 경우에만 `--force`를 붙인다. 직접 불렸다면 스펙의 "남은 질문"과 미달 사실을 보여주고 AskUserQuestion으로 "그래도 진행할까요?"를 한 번 묻는다.
- 오류에 "빠진 고정 항목"이 나오면 스펙 파일에 그 항목을 `- \`ID\` — 설명` 줄로 넣고 다시 시작한다. 인터뷰에서 확정한 것을 빌드가 모르고 지나가지 않게 하기 위해서다.
- 스펙 전체를 읽는다. 특히 **지킬 조건, 하지 않을 것, 다 됐다는 기준, 남은 질문, 코드에서 확인한 것**.
- 기존 코드가 있으면 스펙의 "코드에서 확인한 것"에 적힌 파일을 Read/Grep으로 다시 본다.

시작을 알린다:

> 딥 빌드 시작: {스펙 제목}
> 고정 항목 {n}개, 완료 기준 {n}개. 설계 → 계획 → 검토 → 구현 → 완료 판정까지 이어서 진행합니다. 멈추는 건 한계를 넘었을 때(`stuck`)뿐입니다.

### 2. 설계 문서

`.deep-interview/designs/<slug>.md`를 Write로 쓴다. 네 절이 **모두** 있어야 하고, 각 절은 내용이 있거나 "생략: <이유>" 한 줄이 있어야 한다. 이 스펙에 해당하는 것만 쓰고 억지로 채우지 않는다.

```markdown
# {제목} — 설계

- 스펙: {경로}

## 시퀀스
{주요 흐름 1~3개를 Mermaid sequenceDiagram으로. 누가 누구를 부르고 무엇이 돌아오는지}
또는
생략: {이유 한 줄. 예: 호출 주체가 하나뿐이라 흐름이 자명함}

## 상태
{상태가 바뀌는 대상이 있으면 Mermaid stateDiagram-v2. 예: 신청 → 대기 → 승인/반려}
또는 생략: {이유}

## ERD
{저장하는 데이터가 있으면 Mermaid erDiagram. 엔티티·필드·관계}
또는 생략: {이유}

## API
{외부에 노출하는 엔드포인트·명령·함수가 있으면 표: | 이름 | 입력 | 출력 | 오류 |}
또는 생략: {이유}

## 설계 메모
{스펙의 "남은 질문" 중 설계에서 답이 정해진 것, 선택한 구조와 이유}
```

쓴 뒤 `BD design --file .deep-interview/designs/<slug>.md`로 등록한다. 거부되면 빠진 절을 채운다.

### 3. 계획

설계를 보고 작업 목록을 만든다. 작업은 **그 자체로 테스트할 수 있는 가장 작은 단위**다. superpowers 계획 형식을 따른다: 작업마다 고칠 파일, 인터페이스, 먼저 실패할 테스트.

규칙:
- 스펙의 **모든 고정 항목 ID와 모든 완료 기준 ID**에 담당 작업이 하나 이상 있어야 한다. 없으면 코드가 거부한다.
- `files`는 실제 경로. 새 파일이면 만들 경로.
- `interface`는 이름·시그니처·입출력. "적절히 처리"처럼 추측이 필요한 말은 쓰지 않는다.
- `test`는 작업 전에 실패하고 작업 뒤에 통과할 테스트를 한 문장으로. `test_cmd`는 그 테스트를 실행하는 **셸 명령 그대로**. 구현 단계의 `task-done`이 이 명령만 실행하고, 그때 바꿀 수 없다. `true`·`echo` 같은 빈 명령은 검토자가 거른다.
- `evidence`는 완료 기준(AC) 하나하나를 확인하는 명령. `verify`가 이 명령만 실행한다. 관련 없는 전체 테스트를 모든 AC에 똑같이 붙이지 않는다. 명령으로 확인할 수 없는 기준이 있으면 그 기준을 확인하는 작은 테스트를 작업에 넣는다.
- `depends_on`으로 순서를 적는다. 순환이면 코드가 거부한다. 작업 수가 3개 이하인지 4개 이상인지는 다음 단계(구현)가 방식을 고르는 기준이 된다.
- 스펙의 "하지 않을 것"에 해당하는 작업을 넣지 않는다.

JSON을 임시 파일에 쓰고 `BD plan --input @<경로>`를 실행한다. ID는 `start` 결과에 있는 것만 쓴다.

```json
{
  "tasks": [
    {
      "id": "T1",
      "title": "휴가 신청 저장",
      "files": ["src/leave/request.ts", "src/leave/request.test.ts"],
      "interface": "createRequest({employeeId, start, end, type}) → {id, status:'pending'}; 과거 날짜·초과 일수면 Error",
      "test": "어제 날짜로 신청하면 Error, 오늘 날짜 반차면 status pending",
      "test_cmd": "npm test -- src/leave/request.test.ts",
      "covers": { "fixed": ["화면:신청폼"], "criteria": ["AC-1", "AC-3"] },
      "depends_on": [],
      "notes": "초과 검사는 T3의 잔여 계산을 쓴다"
    }
  ],
  "evidence": {
    "AC-1": { "cmd": "npm test -- src/leave/notify.test.ts", "note": "신청 시 팀장 DM 호출을 검증" },
    "AC-2": { "cmd": "npm test -- src/leave/balance.test.ts" },
    "AC-3": { "cmd": "npm test -- src/leave/request.test.ts -t '과거 날짜'" }
  }
}
```

통과하면 코드가 `.deep-interview/plans/<slug>.md`를 쓴다(작업 목록, 상세, 연결 표, 증거 명령 표). 거부되면 빠진 ID나 빈 필드를 채운다.

### 4. 검토

계획을 쓰지 않은 **새 에이전트 한 명**에게 검토를 맡긴다. Agent 도구로 `subagent_type: "general-purpose"`를 띄우고, 프롬프트에 이 폴더의 `reviewer.md` 전문과 스펙·설계·계획 경로를 넣는다. 읽기만 하고 파일을 고치지 말라고 명시한다. 2회차부터는 직전 지적과 무엇을 고쳤는지도 넣는다.

에이전트가 돌려준 JSON을 임시 파일에 쓰고 `BD review --input @<경로>`로 기록한다.

| 결과 | 할 일 |
|:---|:---|
| `pass` → 상태 `planned` | 5. 구현 시작으로 |
| `revise` → 상태 `revising` | blocker 지적을 설계(2)나 계획(3)에 반영하고 다시 등록 → 다시 검토. 설계만 고쳤으면 `design`만 다시 등록해도 검토로 돌아간다. 검토 3회 안에 통과해야 한다(수정 기회 2번) |
| 3번째 검토도 `revise` → 상태 `stuck` | 구현하지 않는다. 남은 지적을 표로 보여주고 멈춘다 |

검토자의 지적에 동의하지 않을 수 있다. 그래도 근거 없이 넘기지 않는다: 반박이면 왜 스펙에 맞는지 다음 검토 프롬프트에 적고, 검토자가 다시 판단하게 한다.

### 5. 계획 통과 → 구현 시작

`planned`가 되면 멈추지 않고 바로 구현으로 간다. 먼저 짧게 알린다: 설계·계획 경로, 작업 수와 순서(id·제목), 검토 횟수와 마지막 판정 요약. 그리고 `BD execute`를 실행한다.

결과의 `mode`가 방식이다. 작업 수로 코드가 정한다.

| mode | 작업 수 | 방식 |
|:---|:---|:---|
| `single` | 3개 이하 | 이 세션이 순서대로 직접 구현. 끝에 최종 리뷰만 |
| `agents` | 4개 이상 | 작업마다 구현 에이전트가 만들고, 리뷰 에이전트가 검토 |

### 6. 작업 루프

`BD execute`/`task-done`/`task-review` 결과의 `ready_tasks`가 지금 할 수 있는 작업들이다(의존이 끝난 것만, 코드가 가린다). 하나면 그것을, 여럿이면 `agents` 방식에서는 구현 에이전트를 동시에 띄워도 된다. 단, 계획의 `files`가 겹치는 작업은 동시에 하지 않는다(같은 파일을 두 에이전트가 고친다). `task-done`은 한 번에 하나씩 실행한다. 작업 사이에 사용자에게 "계속할까요?"를 묻지 않는다.

계획의 테스트 명령이나 증거 명령 자체가 틀렸으면(경로 오타, 패턴 불일치) 실패를 반복하지 말고 `BD amend --input @<경로>`로 그 명령만 고친다. 고친 작업은 다시 열린다. 다른 필드(파일, 인터페이스, 의존)를 고쳐야 하면 계획의 오류이므로 멈추고 사용자에게 알린다.

**작업 하나의 순서 (`single`)**

1. 계획의 그 작업을 읽는다: 고칠 파일, 인터페이스, 먼저 실패할 테스트, 테스트 명령.
2. 테스트 코드를 먼저 쓰고 계획의 `test_cmd`를 실행해서 **실패를 확인**한다.
3. 인터페이스대로 구현한다. 계획에 적힌 파일만 고친다.
4. `BD task-done --task <id>`를 실행한다. 코드가 계획의 `test_cmd`를 직접 돌려서 종료 코드 0일 때만 완료로 기록한다. 명령은 바꿀 수 없다. 명령이 틀렸다면 그건 계획의 오류이므로 멈추고 사용자에게 알린다.
5. 실패하면 `output_tail`을 보고 고치고 다시 `task-done`. 코드가 시도를 세고, 3회면 전체를 `stuck`으로 멈춘다.

**작업 하나의 순서 (`agents`)**

1. Agent 도구로 `subagent_type: "general-purpose"` 구현 에이전트를 띄운다. 프롬프트에 이 폴더의 `implementer.md` 전문, 스펙·설계·계획 경로, 작업 id를 넣는다. 이 세션의 대화 내용은 넘기지 않는다.
2. 에이전트가 끝났다고 하면 `BD task-done --task <id>`를 실행한다. 에이전트의 "통과했다"는 말을 믿지 않고 코드가 계획의 `test_cmd`를 다시 돌린다.
3. 통과하면 상태가 `awaiting_review`가 된다(그동안 `ready_tasks`에서 빠진다). 새 리뷰 에이전트를 띄운다: `task-reviewer.md` 전문, 경로들, 작업 id, `files_changed`. 읽기 전용이라고 명시한다.
4. 판정 JSON을 임시 파일에 쓰고 `BD task-review --task <id> --input @<경로>`로 기록한다. `revise`면 blocker를 구현 에이전트(같은 에이전트를 SendMessage로 이어가거나 새로 띄움)에게 넘겨 고치게 하고 2부터 다시. `revise`도 실패 횟수로 센다.
5. 에이전트가 `blocked`를 돌려주면 추측으로 메우지 않는다. 막힌 이유가 스펙·계획의 빈 곳이면 `stuck`이 아니어도 멈추고 사용자에게 묻는다.

**멈춤 (`stuck`)**: 끝난 작업, 남은 작업, 실패한 작업과 마지막 이유(`failed_reason`, `output_tail`)를 표로 보여주고 멈춘다. 고치려면 사용자가 정해야 하는 것을 한 줄로 적는다. 다시 하려면 사용자 결정 뒤 `BD start --spec <경로> --restart`로 설계부터 다시 한다(옛 상태는 `builds/`에 보관된다). 끝난 작업의 코드는 남아 있으니 설계·계획은 그것을 반영해 쓴다.

### 7. 완료 판정

모든 작업이 `done`이면:

1. `BD verify`를 실행한다. 코드가 계획의 `evidence` 명령을 완료 기준마다 실행하고 하나라도 0이 아니면 `passed: false`를 돌려준다. 실제 실패가 3회면 `stuck`.
2. 실패한 기준이 있으면 고친다. 작업의 코드를 고쳐야 하면 `BD reopen --task <id>`로 그 작업을 다시 연다(의존 작업도 같이 열린다). 고친 뒤 `task-done`으로 테스트를 다시 통과시키고, `agents` 방식이면 `task-review`까지 받는다. 그리고 `verify`를 다시 한다. 명령 자체가 틀렸으면 `amend`.
3. 통과하면 새 에이전트에게 최종 리뷰를 맡긴다: `final-reviewer.md` 전문, 경로들, `verify` 결과(명령과 출력), 변경된 파일 목록(`git status`·`git diff --stat`), `status` 결과의 `amendments`(구현 중 고친 명령). 읽기 전용이라고 명시한다.
4. 판정을 `BD final-review --input @<경로>`로 기록한다. JSON에는 `criteria`(모든 AC의 ok/weak/fail)가 있어야 하고, fail이나 blocker가 있으면 pass일 수 없다(코드가 거부한다). `revise`면 코드가 blocker 지적이 가리키는 작업(`task`, 또는 `target`의 작업 id·AC id·파일 경로)을 의존 작업까지 자동으로 다시 연다(`reopened_tasks`). 그 작업을 고치고 `task-done`(+ `agents`면 `task-review`) → `verify` → 다시 최종 리뷰. 최대 3회.

### 8. 끝

`done`이면 아래를 보여주고 멈춘다. **커밋은 자동으로 하지 않는다.**

- 변경된 파일 목록과 줄 수 (`git diff --stat`)
- 완료 기준 표: AC id, 기준, 증거 명령, 결과
- 최종 리뷰 요약과 남은 `minor` 지적
- 구현 중에 정한 것 (에이전트 `notes`, 스펙의 "남은 질문"에 답이 된 것)
- AskUserQuestion으로 커밋 여부를 묻는다: `커밋하기`, `변경만 두기`, `되돌리기`

`stuck`이면 6의 멈춤 형식으로 보여준다.

## 지키는 규칙

1. **스펙이 기준이다.** 설계·계획·코드가 스펙과 충돌하면 스펙을 따른다. 스펙이 틀렸다고 생각되면 고치지 말고 사용자에게 알린다.
2. **설계·계획 단계에서는 소스 코드를 고치지 않는다.** 구현은 `execute` 뒤에만 한다.
3. **숫자·연결·통과는 코드가 본다.** 고정 항목·완료 기준 연결, 검토·시도 횟수, 테스트 통과, 증거 명령 결과는 `build.mjs`가 센다. 테스트 명령과 증거 명령은 계획에 고정돼 검토를 거친 것만 쓴다. 에이전트가 "통과했다"고 해도 코드로 다시 돌린다.
4. **검토자와 리뷰어는 새 에이전트다.** 이 세션이 스스로 검토하지 않는다. 구현 에이전트에게 이 세션의 대화를 넘기지 않는다.
5. **테스트를 지우거나 건너뛰게 만들어서 통과시키지 않는다.** 그렇게 해야만 통과한다면 멈추고 사용자에게 알린다.
6. **커밋·푸시는 하지 않는다.** 끝나면 묻는다.
7. **글은 사용자의 CLAUDE.md 규칙**을 따른다: 한국어, 결론 먼저, 표, 짧은 문장.

## 이어하기

`BD status`로 상태를 본다. `designing`이면 2부터, `planning`이면 3부터, `reviewing`이면 4부터, `revising`이면 마지막 지적을 보고 2 또는 3부터, `planned`면 5부터, `executing`이면 `ready_tasks`·`awaiting_review_tasks`부터(둘 다 없으면 7부터), `done`/`stuck`이면 8을 다시 보여준다.

세션이 바뀌어(`/clear` 등) `exists: false`가 나오는데 `.deep-interview/builds/`에 이전 세션 파일이 있으면, 그 파일 이름(세션 ID)으로 `--session <옛 ID>`를 붙여 이어갈 수 있다. 사용자에게 어느 빌드인지 확인하고 한다.
