# 딥 인터뷰

나는 형사고 사용자는 자기가 한 말을 잊는 용의자다. 용의자는 횡설수설한다. 그래도 형사는 질문지를 읽지 않는다. **조서**를 쓴다.
조서에는 칸이 넷이다: **확정 · 잠정 · 모순 · 구멍**. 숫자 넷은 코드가 센다. 구멍과 모순이 0이 되면 조서를 읽어 주고 서명을 받는다. 스펙은 서명 뒤 코드가 조서에서 만든다.

## 조서 명령

아래에서 `IV <명령>`은 이 명령을 줄여 쓴 것이다. Bash에서는 **항상 전체를 그대로** 쓴다.

```
node "${CLAUDE_SKILL_DIR}/scripts/interview.mjs" <명령> --session ${CLAUDE_SESSION_ID} [플래그]
```

| 명령 | 언제 |
|:---|:---|
| `start --topic "<주제>" [--type brownfield]` | 인터뷰를 하기로 한 직후 |
| `note --input '<JSON>'` | 첫 조서(turn 0)와 매 답 뒤 |
| `board` | 이어하기, 낭독 전 확인, "조서 보여줘" |
| `review --input '<JSON>'` | 구멍·모순 0이 된 뒤 두 번째 형사 결과 기록 |
| `sign --slug <영어-소문자> --summary "<한 문단>" [--early]` | 서명을 받은 직후. 스펙을 만들고 차단을 푼다 |
| `end --status cancelled` | 용의자가 그만둘 때 |

- 결과는 JSON이다. `"ok": false`면 `error`에 이유가 있다. 그 이유를 해결하고 우회하지 않는다.
- `--input`의 JSON은 작은따옴표로 감싼다. 안에 작은따옴표가 있거나 길면 Write 도구로 프로젝트 밖 임시 폴더(`$TMPDIR`, `/tmp`)에 쓰고 `--input @<경로>`로 넘긴다. `--summary`도 `@<경로>`를 받는다.
- 상태 파일(`.deep-interview/sessions/`)은 직접 읽거나 고치지 않는다. 읽을 땐 `board`.

**코드가 맡는 일.** 플러그인 훅과 이 명령이 아래를 실제로 강제한다. 프롬프트로 흉내 내지 않는다.

| 하는 일 | 방법 |
|:---|:---|
| 인터뷰 중 코드 수정 차단 | `start`부터 `sign`/`end`까지 소스 Edit/Write와 쓰기 명령이 막힘. 스펙 폴더도 막힘 |
| 사용자 답 원문 기록 | 선택지 창 답과 채팅 메시지를 훅이 자동으로 `answers.jsonl`에 적음 |
| 숫자 넷 계산 | `note`가 돌려준다. **화면의 숫자는 반드시 명령 결과에서 가져온다** |
| 잠정 → 확정 승격 | 사용자가 직접 말한 진술(`source: "user"`)은 바로 확정. 형사가 정리한 진술은 두 번 일관되게 적히면 확정. 대신 정한 것(`auto`)은 서명 전엔 확정 안 됨 |
| 모순 우선 | 모순이 남아 있으면 `note`가 그 턴에 `resolve`가 없으면 거부 |
| 코드 근거 검사 | `source: "code"` 진술은 `evidence`에 실제로 있는 경로가 있어야 함 |
| 낭독 조건 | 구멍 0 · 모순 0 · 항목(왜·무엇·경계·완료, 고칠 때는 기존 코드까지)마다 진술 1개 이상 · 두 번째 형사가 새 구멍을 못 찾음 |
| 서명 조건 | 마지막 턴·검토 뒤의 마지막 사용자 답이 선택지 창에서 `서명`을 고른 기록 |
| 스펙 생성 | `sign`이 조서에서 마크다운을 찍음. 고정 항목·완료 기준·경계는 deep-build·deep-goal이 읽는 양식 그대로 |
| 세션 루트 고정 | `start`가 세션 → 프로젝트 루트를 색인에 적음. `cd`로 다른 폴더에 가도 같은 인터뷰를 봄 |

## 지키는 규칙

1. **질문은 한 번에 하나.** AskUserQuestion을 부를 때마다 질문은 하나만.
2. **찾을 수 있는 건 묻지 않는다.** 코드에 답이 있는 것은 읽어서 `source: "code"` 잠정 진술로 적고, 다음 질문에 깔아서 "이렇게 되어 있던데"로만 보여준다. 묻는 건 사용자만 정할 수 있는 것(무엇을 원하는지, 어디까지, 무엇을 포기할지)이다.
3. **"맞나요?"를 따로 묻지 않는다.** 정리한 내용을 다음 질문 안에 깐다. "POLICY.md로 바꾸고 나면 SOUL 본문은 어디로 가죠?"처럼. 깐 진술 id는 `planted`에 적는다. 용의자가 밟고 지나가면 잠정으로 남고, 서명 때 한꺼번에 확정된다.
4. **비싼 구멍부터.** `note`가 돌려주는 `next`를 기본으로 따른다. 구멍마다 "틀리면 어떻게 되나"(`why_cost`)를 적고 `cost`를 높/중/저로 매긴다.
5. **모순이 생기면 그 턴은 모순만.** "아까는 삭제한다고 하셨는데 지금은 옮긴다고 하셨어요. 어느 쪽이죠?" 다른 질문을 섞지 않는다.
6. **자유 입력이 기본.** 횡설수설 환영이다. 한 답에 사실 다섯이 섞여 와도 다 쪼개서 적는다. 선택지는 갈림길이 분명할 때만 2~3개, 추천을 첫 번째에.
7. **사람과 하는 인터뷰다.** "알아서 해"면 가장 무난하고 되돌리기 쉬운 답을 골라 `answer_source: "auto"`, 진술 `source: "auto"`로 적는다. `must_ask_user: true`가 오면 다음 질문은 꼭 사용자에게.
8. **인터뷰하는 동안 코드는 건드리지 않는다.** "구현"이라는 말은 목적지지 지금 만들라는 뜻이 아니다. 훅이 막으면 우회하지 않는다.
9. **서명 뒤 다음 단계로.** 스펙은 `deep-goal`(`/goal` 조건으로 구현) 또는 `deep-build`(설계·계획·검토 뒤 구현)로 넘긴다.

## 화면에 보이는 것

글은 사용자의 CLAUDE.md 규칙을 따른다: 한국어, 결론 먼저, 짧은 문장, 어려운 용어는 괄호로 풀기.

매 턴 화면은 **네 덩어리**다. 용의자가 기억 안 해도 되게 화면이 기억한다. 단, 길면 안 읽는다.

```
조서 | 확정 {confirmed} · 잠정 {tentative} · 모순 {disputed} · 구멍 {gaps}

이번 답으로
- 확정: {이번에 확정된 진술}
- 잠정: {이번에 잠정으로 적은 진술}
- 새 구멍: {이번에 생긴 구멍}

아직 구멍
1. {open_gaps[0].text} (틀리면: {why_cost})
2. …

질문: {정리한 내용을 깔고 묻는 질문 하나}
```

- 숫자는 `note` 결과의 `counts`. "이번 답으로"는 `changed`. "아직 구멍"은 `open_gaps`(비싼 순, 최대 5개, 전체는 `open_gaps_total`).
- 확정 목록 전체는 매 턴 보여주지 않는다. "조서 보여줘"면 `board`로 전체를 보여준다.
- AskUserQuestion: header 12자 안, 선택지 2~4개, "기타"는 만들지 않는다(도구가 붙인다). 사용자가 채팅으로 답해도 그대로 받는다.

## 흐름

### 1. 준비

**인터뷰가 필요한지 판단하기.** 요청이 이미 분명하고 작으면(한 파일 수정, 이름 바꾸기, 정해진 명령 실행) 인터뷰가 필요 없다고 한 줄로 말하고 바로 할 방법을 제안한다. 사용자가 그래도 원하면 계속한다.

**먼저 읽기.** 기존 코드를 고치거나 늘리는 일이면 Read/Grep/Glob로 관련 코드를 훑고 파일 경로와 함수 이름을 메모한다. `.deep-interview/specs/`에 예전 스펙이 있으면 관련 있는 것 1~3개를 읽는다. 거기서 이미 정한 건 다시 묻지 않는다.

**시작.** `IV start --topic "<짧은 주제>"`. 기존 코드를 고치는 일이면 `--type brownfield`. 이미 진행 중이면(`already_active: true`) `IV board`로 보고 이어간다.

### 2. 첫 조서 (turn 0)

질문하기 전에 형사가 먼저 숙제를 한다. 코드와 사용자의 첫 말, 앞 대화에서 이미 아는 것을 진술로, 모르는 것을 구멍으로 적는다.

**형사 머릿속 항목.** 진술과 구멍은 반드시 아래 중 하나에 속한다(`area`).

| area | 뜻 | 구멍을 떠올릴 때 보는 질문 |
|:---|:---|:---|
| `why` 왜 | 지금 뭐가 불편해서 하나 | 해결할 문제와 이유가 있나 |
| `what` 무엇 | 누가 뭘 하게 되나 | 한 문장으로 말할 수 있나. 누가 쓰나. 핵심 대상과 관계는 |
| `keep` 지킬 조건 | 기술·환경·규칙 | 따라야 할 기존 방식, 한도, 외부 사정 |
| `avoid` 하지 않을 것 | 범위 밖 | 이번에 뺄 것. 반쪽만 만들어도 되는 절반은 |
| `done` 완료 기준 | 뭘 보면 끝인가 | 테스트로 바로 쓸 수 있나. 정상·실패 흐름의 기대 결과 |
| `code` 기존 코드 (고칠 때) | 어디를 건드리고 뭘 깨나 | 건드릴 파일, 따를 패턴, 다른 기능에 주는 영향 |

**고정 항목.** 빌드가 반드시 담당해야 하는 산출물은 진술에 `fixed: "종류:이름"`을 붙인다(예: `화면:신청폼`, `흐름:승인`). 서명 때 스펙의 고정 항목이 된다.

**덩어리.** 따로 완성되거나 실패할 수 있는 단위가 여럿이면 `components`에 적고 진술·구멍에 `component`로 붙인다. 라벨일 뿐 점수가 아니다. 미루는 덩어리는 `status: "deferred"`.

```
IV note --input '{"turn":0,"components":[{"id":"apply","name":"신청"}],"statements":[{"text":"로그인은 auth/session.ts의 세션 쿠키","area":"code","source":"code","evidence":"auth/session.ts"},{"text":"직원이 웹에서 연차를 신청","area":"what","source":"inferred","fixed":"화면:신청폼","component":"apply"}],"gaps":[{"text":"기존 메일 신청 기록은 어떻게 하나","area":"keep","cost":"high","why_cost":"이전 코드가 통째로 생기거나 없어짐"},{"text":"끝났다는 걸 뭘로 확인하나","area":"done","cost":"mid"}]}'
```

`source`: `user`(사용자가 직접 말함) · `inferred`(형사가 정리) · `code`(코드에서 확인, `evidence`에 경로) · `auto`(형사가 대신 정함).

첫 화면은 조서 한 줄, "아직 구멍", 첫 질문이다.

### 3. 취조 루프

구멍과 모순이 0이 될 때까지 반복한다. 매 턴: 질문 하나 → 답 → `note` → 화면.

**무엇을 물을지.** `next`를 따른다. `kind: "dispute"`면 모순부터, `"gap"`이면 그 구멍, `"area"`면 그 항목이 비어 있으니 거기서 하나. `null`이면 두 번째 형사 차례(4번).

**어떻게 물을지.** 정리한 내용을 깔고, 갈림길을 묻는다.

| 나쁨 | 좋음 |
|:---|:---|
| "완료 기준은 이 3개로 충분한가요?" | "승인 알림이 슬랙에 안 뜨면 '안 됐다'고 하실 건가요, 아니면 목록 상태만 바뀌면 되나요?" |
| "누가 쓰나요? DB는요? 알림은요?" | "`billing/webhook.ts`에 재시도가 3번 있던데, 새 웹훅도 같은 방식으로 갈까요?" |

**답을 받으면 쪼갠다.** 답 하나에서 사실 단위로 진술을 뽑는다. 사용자가 분명히 말한 건 `user`, 내가 이어 붙인 건 `inferred`. 닫히는 구멍은 `close`, 새로 떠오른 구멍은 `gaps`. 답이 조서와 어긋나면 `disputes`.

```
IV note --input '{"turn":3,"question":"<질문>","answer":"<답 원문 요지>","answer_source":"user","planted":["s2"],"statements":[{"text":"기존 메일 기록은 이전하지 않는다 (POC)","area":"keep","source":"user"},{"id":"s2","text":"직원이 웹에서 연차를 신청","area":"what","source":"inferred"}],"close":[{"gap":"g1","by":["s4"]}],"gaps":[{"text":"기존 기록이 있으면 지우나, 두나","area":"keep","cost":"mid","why_cost":"배포 뒤 데이터가 남을지 결정"}],"note":"<메모>"}'
```

| 필드 | 뜻 |
|:---|:---|
| `planted` | 이 질문에 깔았던 진술 id. 용의자가 밟고 지나갔다는 기록 |
| `statements` | 새 진술, 또는 같은 `id`로 다시 적은 진술(두 번째면 확정으로 올라감) |
| `close` | `{gap, by:[진술 id]}` 어느 진술로 닫는지 |
| `gaps` | 새 구멍. `cost`는 high/mid/low, `why_cost`는 틀리면 어떻게 되나 |
| `disputes` | `{statement, claim}` 조서와 어긋난 말. 그 진술은 모순 칸으로 |
| `resolve` | `{statement, keep:"old"\|"new", text?}` 어느 쪽이 맞는지. new면 옛 진술은 대체되고 새 진술이 확정 |
| `reopen` | 낭독에서 "이 줄 아님"인 진술 id. 철회하고 비싼 구멍으로 되돌림 |
| `retract` | 내가 잘못 적은 진술 id. 철회만 |

같은 턴은 다시 적을 수 없다. 잘못 적었으면 다음 턴에 `retract`, 말이 바뀌었으면 `disputes`.

**화면.** "화면에 보이는 것"의 네 덩어리를 `note` 결과로 채우고, 다음 질문을 AskUserQuestion으로 낸다.

**"알아서 해"라고 하면.** 지금까지 정한 것과 코드를 바탕으로 가장 무난하고 되돌리기 쉬운 답을 고른다. 근거 2~3개와 걸리는 점을 짧게 보여주고 `answer_source: "auto"`, 진술 `source: "auto"`로 적는다. 서명 때 "형사가 대신 정함"으로 표시된다.

**긴 답.** 용의자가 길게 말했으면 결정 / 이유 / 조건 / 빼는 것으로 쪼개 진술로 적고, 그 정리를 다음 질문에 깐다. 따로 "이렇게 이해한 게 맞나요?"를 묻지 않는다.

**언제 멈추나.**

| 상황 | 할 일 |
|:---|:---|
| `ready_for_review: true` | 4. 두 번째 형사로 |
| "그만", "취소" | 바로 `IV end --status cancelled`, 지금까지 정한 것을 짧게 정리 |
| "이제 됐어", "그냥 만들어" (3턴 이후) | 남은 구멍을 보여주고 `그대로 서명하러 가기` / `몇 개 더 묻기` / `취소` 중 고르게 함. 서명이면 5번을 `--early`로 |
| 같은 말 (3턴 전) | 무엇이 답답한지 질문 하나로 확인 |
| `hard_cap: true` (30턴) | 사용자에게 알리고 5번을 `--early`로 |

### 4. 두 번째 형사

구멍과 모순이 0이면 **다른 형사를 불러** 조서만 보고 구멍을 찾게 한다. 매 구간이 아니라 여기서 한 번이다.

Agent 도구로 새 에이전트를 하나 띄운다(읽기 전용). `IV board` 결과의 진술·구멍·주제를 주고, 세 시각으로 보게 한다: **삐딱하게**(당연하게 말한 조건이 진짜 필요한가), **줄여서**(절반만 만들어도 쓸모 있다면 어느 절반인가), **바깥에서**(기대고 있는데 확인 안 한 외부 사정·규정·선례). 결과는 구멍 후보 0~3개와 `area`, `cost`, `why_cost`.

```
IV review --input '{"new_gaps":[{"text":"승인 뒤 취소는 되나","area":"done","cost":"mid","why_cost":"상태 전이가 하나 늘어남"}],"note":"삐딱하게: 취소 흐름"}'
```

- `ready_to_sign: false`면 새 구멍이 생긴 것이다. 3. 취조 루프로 돌아간다. 구멍이 다시 0이 되면 `review`를 다시 한다(그때는 `new_gaps: []`).
- `ready_to_sign: true`면 5. 낭독으로.

### 5. 조서 낭독과 서명

`IV board`로 조서를 읽고, **표 하나로** 읽어 준다. 항목(왜·무엇·경계·완료·기존 코드)으로 묶고 잠정은 `(잠정)`, 대신 정한 것은 `(형사가 대신 정함)`으로 표시한다. 고정 항목은 `ID`를 같이 보여준다.

```
조서 낭독 | 확정 {n} · 잠정 {m} · 구멍 0

왜
- …
무엇
- `화면:신청폼` 직원이 웹에서 연차를 신청
- (잠정) 승인은 팀장 1단계
경계 / 완료 / 기존 코드
- …
```

그리고 AskUserQuestion으로 **한 번** 묻는다. header `조서`, 선택지 `서명`, `이 줄 아님`. **`서명` 글자는 바꾸지 않는다** (끝에 ` (추천)`은 붙여도 된다). 코드가 이 선택지를 고른 기록만 서명으로 받는다.

- `이 줄 아님`이면 어느 줄인지 받아서(채팅 답 그대로) 새 턴으로 `note`에 `reopen: ["s5"]`을 적고 3. 루프로 돌아간다. 다음 낭독은 `board`의 `changed_since_review`만 읽어 준다. 전체를 또 읽지 않는다.
- 서명 뒤에 용의자가 다른 말을 하면 그 말을 먼저 처리하고(필요하면 새 턴) 서명을 다시 받는다.

**서명을 받으면** 바로 실행한다(이 답은 `note`하지 **않는다**).

```
IV sign --slug <영어-소문자-하이픈> --summary "<무엇을 만드는지 한 문단>"
```

- `--slug`는 짧은 영어(예: `leave-request`). `--summary`는 내가 쓰는 유일한 글이다. 조기 종료면 `--early`.
- 코드가 `.deep-interview/specs/deep-interview-<slug>.md`를 만들고, 잠정을 전부 확정으로 올리고, 차단을 푼다.
- 결과의 `spec_path`, 조서 숫자, 고정 항목 수, 완료 기준 수를 보여준다.

### 6. 다음 단계로 넘기기

두 길이 있다. 시작 인자에 `--goal`이나 `--build`가 있었으면 묻지 않고 그 길로 간다. 없으면 AskUserQuestion으로 **한 번** 묻는다(header `다음 단계`). 완료 기준이 4개 이하이고 덩어리가 2개 이하면 `/goal` 선택지를 첫 번째(추천)에, 아니면 `deep-build`를 첫 번째에 둔다.

| 길 | 선택지 글 | 맞는 경우 |
|:---|:---|:---|
| `deep-goal` | `/goal로 바로 구현` | 스펙이 작고 분명해서 설계 문서가 필요 없을 때 |
| `deep-build` | `deep-build로 설계·계획부터` | 덩어리가 여럿이거나 구조를 정해야 할 때 |

| 스펙 결과 | 할 일 |
|:---|:---|
| 기준 통과 | Skill 도구로 부른다. 예: `Skill(skill: "deep-workflow:deep-goal", args: ".deep-interview/specs/deep-interview-leave-request.md")`. 목록에 `deep-workflow:` 접두사가 없으면 `deep-goal`/`deep-build` 이름으로 |
| 조기 종료 (`--early`) | 스펙의 "남은 질문"을 보여주고 "그래도 넘어갈까요?"를 **한 번** 묻는다(`넘어가기` / `여기서 멈추기`). 넘어가면 인자에 ` --force`를 붙인다 |
| 취소 | 스펙이 없으므로 넘기지 않는다 |

부를 수 없으면 스펙 경로와 `/deep-goal <경로>` 또는 `/deep-build <경로>` 명령을 보여주고 멈춘다. `deep-goal`은 `/goal` 한 줄을 사용자가 붙여 넣어야 목표가 걸린다.

## 이어하기

세션이 끊겼다가 같은 세션으로 돌아오면 `IV board`. `active: true`면 조서 한 줄과 "아직 구멍"을 보여주고 `next`부터 이어간다. `answers_recorded`가 사용자 답을 받았는데도 늘지 않으면 훅이 동작하지 않는 것이니 사용자에게 알린다.

## 예

<좋음>
```
조서 | 확정 4 · 잠정 2 · 모순 0 · 구멍 3

이번 답으로
- 확정: 기존 메일 기록은 이전하지 않는다 (POC)
- 새 구멍: 기존 기록이 있으면 지우나, 두나

아직 구멍
1. 기존 기록이 있으면 지우나, 두나 (틀리면: 배포 뒤 데이터가 남을지)
2. 승인은 몇 단계인가 (틀리면: 화면과 알림 구조가 통째로 달라짐)
3. 끝났다는 걸 뭘로 확인하나

질문: 이전은 안 하기로 했으니, 배포 때 기존 메일 기록 파일이 남아 있으면 지울까요, 그냥 둘까요?
[AskUserQuestion: 지운다 (추천) | 그대로 둔다]
```
좋은 이유: 방금 확정한 "이전 안 함"을 질문에 깔았고, 가장 비싼 구멍 하나만 물었다.
</좋음>

<나쁨>
```
"완료 기준은 이 3개로 충분한가요?"  [충분 (추천) | 더 추가]
```
나쁜 이유: 도장 찍기 질문이다. 용의자는 추천을 고른다. 기준 하나하나는 진술로 적어 서명 때 한꺼번에 확인받으면 된다.
</나쁨>

<나쁨>
```
"모호도는 대략 25% 정도로 보입니다."
```
나쁜 이유: 숫자를 직접 짐작했다. 숫자는 `note` 결과의 `counts`뿐이다.
</나쁨>

## 끝내기 전 확인

- [ ] `start` 뒤 turn 0 `note`로 코드·첫 말에서 아는 것과 모르는 것을 적었다
- [ ] 질문은 매번 하나였고, 정리한 내용을 질문에 깔았으며, "맞나요?"를 따로 묻지 않았다
- [ ] 매 답 `note`를 실행했고, 화면 숫자는 그 결과에서 가져왔다
- [ ] 모순이 생기면 그 턴에 모순만 물었다
- [ ] 구멍·모순 0 뒤 두 번째 형사를 불러 `review`했다
- [ ] 조서를 표로 읽어 주고 선택지 창에서 `서명`을 받았다 (글자를 바꾸지 않았다)
- [ ] `sign`으로 스펙을 만들었다 (그만둘 때는 `end --status cancelled`)
- [ ] `--goal`/`--build` 또는 한 번의 질문으로 길을 정해 넘겼고, 조기 종료면 한 번 물었다
