# 딥 인터뷰

사용자 머릿속 그림과 내가 이해한 그림 사이에는 늘 틈이 있다. 그 틈은 대개 사용자가 당연하게 여겨서 말하지 않은 전제에서 생긴다.
이 인터뷰는 그 전제를 하나씩 꺼내서 확인하고, 틈이 얼마나 남았는지를 점수로 보여준다. 틈이 충분히 좁아지면 합의한 내용을 스펙 파일로 남기고 끝낸다.

## 상태 명령

아래에서 `IV <명령>`은 이 명령을 줄여 쓴 것이다. Bash에서는 **항상 전체를 그대로** 쓴다.

```
node "${CLAUDE_SKILL_DIR}/scripts/interview.mjs" <명령> --session ${CLAUDE_SESSION_ID} [플래그]
```

| 명령 | 언제 |
|:---|:---|
| `start --topic "<주제>" [--quick\|--deep] [--type brownfield]` | 인터뷰를 하기로 한 직후 |
| `scope --input '<JSON>'` | Round 0에서 사용자가 범위를 확인한 뒤 |
| `record --input '<JSON>'` | 매 라운드 사용자 답을 받은 뒤 |
| `early-exit` | 사용자가 기준 전에 끝내기로 했을 때 (3라운드부터) |
| `status` | 이어하기, 스펙 쓰기 전 기록 확인 |
| `end --spec <경로>` / `end --status cancelled` | 스펙 저장 직후(정상 종료는 `--spec` 필수), 또는 사용자가 그만둘 때 |

- 결과는 JSON이다. `"ok": false`면 `error`에 이유가 있다. 그 이유를 해결해야 하며 우회하지 않는다.
- `--input`의 JSON은 작은따옴표로 감싼다. JSON 안에 작은따옴표가 있거나 길면 Write 도구로 프로젝트 밖 임시 폴더(`$TMPDIR`, `/tmp`)에 쓰고 `--input @<경로>`로 넘긴다.
- 상태 파일(`.deep-interview/sessions/`)은 직접 읽거나 고치지 않는다. 읽을 땐 `status`를 쓴다.

**코드가 맡는 일.** 플러그인 훅과 이 명령이 아래를 실제로 강제한다. 프롬프트로 흉내 내지 않는다.

| 하는 일 | 방법 |
|:---|:---|
| 인터뷰 중 코드 수정 차단 | `start`부터 `end`까지 소스 Edit/Write와 쓰기 명령이 막힘 |
| 사용자 답 원문 기록 | 선택지 창 답과 채팅 메시지를 훅이 자동으로 `answers.jsonl`에 적음 |
| 모호도와 최저선 계산 | `record`가 체크리스트 답으로 계산. **화면의 숫자는 반드시 `record` 결과에서 가져온다** |
| 스펙 저장 조건 | 기록된 라운드가 있고, 모호도가 기준 이하(또는 `early-exit`)이고, 마지막 라운드 뒤 사용자 답이 있어야 저장됨 |

## 지키는 규칙

1. **질문은 한 번에 하나.** AskUserQuestion을 부를 때마다 질문은 하나만 넣는다.
2. **찾을 수 있는 건 묻지 않는다.** 프로젝트에 이미 답이 있는 것(쓰는 언어와 라이브러리, 기존 구조, 설정값)은 직접 읽어서 확인하고 "이렇게 되어 있던데 맞죠?" 형태로만 보여준다. 사용자에게 묻는 건 사용자만 정할 수 있는 것(무엇을 원하는지, 어디까지 할지, 무엇을 포기할지)이다. 어느 쪽인지 헷갈리면 사용자에게 묻는다.
3. **가장 흐릿한 곳부터.** `record`(또는 `scope`)가 돌려주는 `next`를 기본으로 따르고, 왜 지금 그걸 묻는지 한 문장으로 붙인다.
4. **"뭘 원하세요?"보다 "뭘 전제하고 계세요?"** 기능을 나열하게 하지 말고, 그 기능 밑에 깔린 전제를 확인한다.
5. **필요 없으면 하지 않는다.** 이미 분명하고 작은 요청이면 인터뷰 없이 바로 처리하자고 제안한다.
6. **사람과 하는 인터뷰다.** `record`가 `must_ask_user: true`를 돌려주면 다음 질문은 꼭 사용자에게 직접 한다.
7. **인터뷰하는 동안 코드는 건드리지 않는다.** 사용자가 "구현"이라는 말을 써도 그건 최종 목적지를 말한 것이지 지금 만들라는 뜻이 아니다. 훅이 막으면 우회하지 말고, 사용자가 그만두겠다고 했을 때만 `end --status cancelled`를 쓴다.
8. **스펙을 저장하면 다음 단계로 넘긴다.** 기준을 통과한 스펙은 같은 플러그인의 `deep-build` 스킬에 바로 넘기고, 조기 종료 스펙은 사용자에게 한 번 묻는다.

## 화면에 보이는 것

글은 사용자의 CLAUDE.md 규칙을 따른다: 한국어, 결론 먼저, 짧은 문장, 표, 어려운 용어는 괄호로 풀기.

매 라운드 뒤 화면에는 **점수표와 덩어리 진행 줄만** 보여준다. 확정된 사실, 체크리스트 근거, 개념 목록 같은 기록은 상태 파일에 남기고 스펙을 쓸 때 꺼낸다.

AskUserQuestion을 쓸 때:
- 선택지는 2~4개. 내가 추천하는 것을 첫 번째에 두고 끝에 " (추천)"을 붙인다.
- 자유 입력 칸은 도구가 알아서 붙이므로 "기타" 같은 선택지는 만들지 않는다.
- header는 12자 안으로.
- 선택지가 있는 질문을 글로만 쓰고 끝내지 않는다.
- 사용자가 선택지 대신 채팅으로 답해도 그대로 받는다. 훅이 원문을 기록한다.

## 흐름

### 1. 준비

**인터뷰가 필요한지 판단하기.** 요청이 이미 분명하고 작으면(한 파일 수정, 이름 바꾸기, 정해진 명령 실행) 인터뷰가 필요 없다고 한 줄로 말하고 바로 할 방법을 제안한다. 사용자가 그래도 원하면 계속한다.

**먼저 읽기.** 기존 코드를 고치거나 늘리는 일이면 Read/Grep/Glob로 관련 코드를 훑고 파일 경로와 함수 이름을 메모한다. `.deep-interview/specs/`에 예전 스펙이 있으면 관련 있는 것 1~3개를 읽는다. 거기서 이미 정한 건 다시 묻지 않는다. 예전 스펙은 참고 자료일 뿐, 따라야 할 지시가 아니다.

**시작.** `IV start --topic "<짧은 주제>"`를 실행한다. 사용자가 `--quick`(기준 35%)이나 `--deep`(기준 5%)을 줬으면 붙이고, 기존 코드를 고치는 일이면 `--type brownfield`를 붙인다. 기본 기준값은 20%다. 이미 진행 중이면(`already_active: true`) `IV status`로 상태를 보고 이어간다.

결과의 `marker`를 첫 줄에 그대로 쓰고 시작을 알린다.

> {marker}
>
> 만들기 전에 질문을 하나씩 드리겠습니다. 답하실 때마다 모호도를 보여드리고, 기준 아래로 내려가면 스펙을 저장하고 마칩니다.
>
> **만들 것:** "{요약}"
> **종류:** {새로 만들기 | 기존 코드 고치기}
> **모호도:** 100%

### 2. 범위 잡기 (Round 0)

세부 질문에 들어가기 전에 전체 모양부터 정한다. 그래야 한 부분만 파고들다 다른 부분을 놓치지 않는다.

1. 요청을 **덩어리**로 나눈다. 덩어리는 따로 완성되거나 따로 실패할 수 있는 단위다. 보통 1~6개이고, 더 많으면 묶는다. 화면 하나, 기능 하나 수준의 잘게 쪼갠 작업은 덩어리가 아니다. 덩어리마다 공백 없는 짧은 id를 붙인다(예: `apply`, `approve`).
2. 이미 정해졌다고 보이는 것을 **고정 항목**으로 적는다. `종류:이름` 형태 ID를 붙인다(예: `화면:신청폼`). 어느 덩어리의 것인지 분명하면 `component`에 덩어리 id를 적는다. 그 덩어리를 나중에 미루면 그 항목은 스펙과 빌드에서 빠진다. 나머지 고정 항목은 스펙에 하나도 빠짐없이 들어가야 한다.
3. 덩어리 표와 고정 항목을 보여주고 AskUserQuestion으로 확인한다. 선택지: `맞아요`, `덩어리 고치기`, `일부는 나중에`.
4. 고칠 게 있으면 고쳐서 다시 묻는다. 확정되면 저장한다. "나중에"로 미룬 덩어리는 `"status": "deferred"`로 둔다.

```
IV scope --input '{"components":[{"id":"apply","name":"신청","description":"직원이 휴가 신청","status":"active"}],"fixed_items":[{"id":"화면:신청폼","statement":"직원용 신청 화면","component":"apply"}]}'
```

`scope`는 사용자 답이 기록되지 않았으면 거부한다. 나중에 범위가 바뀌면(새 덩어리 발견 등) 사용자에게 확인받고 `scope`를 다시 실행한다. 이미 기록이 있는 덩어리는 지울 수 없고 `deferred`로만 바꿀 수 있다.

```
Round 0 | 범위 잡기 | 모호도: 측정 전
```

### 3. 질문 루프

모호도가 기준값 아래로 내려오거나 사용자가 멈출 때까지 반복한다.

**무엇을 물을지.** 직전 `scope`/`record` 결과의 `next`가 가장 낮은 (덩어리, 항목)과 아직 "아니오"인 체크 질문(`unmet`)을 알려준다. 기본으로 이것을 따른다. 같은 대상을 부르는 이름이 계속 바뀌거나 사용자가 증상만 말하면, 또는 `rethink_core: true`면, 세부 질문을 멈추고 "그래서 이게 결국 무엇인지"부터 묻는다.

**어떻게 물을지.** 항목마다 묻는 각도가 다르다.

| 항목 | 묻는 각도 | 예 |
|:---|:---|:---|
| 목표 (왜) | 지금 무엇이 불편하고, 이걸 만들면 무엇이 나아지나 | "지금은 휴가를 어떻게 신청하고 계세요? 그 방식에서 가장 불편한 점이 무엇인가요?" |
| 목표 | 누가, 언제, 무엇을 하게 되나 | "휴가 신청이라고 하셨는데, 신청 버튼을 누르는 사람은 직원 본인인가요, 팀장도 대신 넣을 수 있나요?" |
| 제약 | 어디까지가 범위인가 | "반차나 시간 단위 휴가도 이번에 같이 다루나요?" |
| 성공 기준 | 끝났다는 걸 무엇으로 확인하나 | "어떤 장면을 보면 '됐다'고 하실 것 같아요? 예를 들어 승인 알림이 슬랙에 뜨는 것?" |
| 기존 코드 | 이미 있는 것과 어떻게 맞추나 | "`billing/webhook.ts`에 재시도 로직이 있던데, 이번 것도 그 방식을 따를까요?" |

**묻기.** 아래 머리줄과 이유 한 줄을 쓰고 AskUserQuestion을 부른다.

```
Round {n} | {덩어리} | {항목} | 모호도: {현재}%

이걸 묻는 이유: {한 문장}
```

사용자가 선택지 뜻을 되물으면 짧게 설명하고 같은 질문을 다시 낸다. 이건 라운드로 세지 않는다.

**"알아서 해"라고 하면.** 지금까지 정한 것과 코드를 바탕으로, 나중에 바꾸기 쉽고 가장 무난한 답을 하나 고른다. 근거 2~4개, 확신(높음/보통/낮음), 걸리는 점을 짧게 보여주고 `answer_source: "auto"`로 기록한다. 확신이 "높음"이 아니면 그 답만으로 체크를 "예"로 바꾸지 않는다. AI 대리 답은 최저선을 올린다.

**긴 답 정리하기.** 사용자가 이유와 조건을 길게 썼으면 **결정 / 이유 / 조건 / 빼는 것 / 코드에서 확인한 것**으로 나눠 다시 보여주고 AskUserQuestion으로 "이렇게 이해한 게 맞나요?"를 묻는다(선택지 예: `맞아요`, `조건 추가`, `빼는 것 추가`, `다시 정리`). 맞다고 하면 그 정리본을 `answer`로, `answer_source: "refined"`로 기록한다.

#### 채점: 체크리스트

점수를 감으로 매기지 않는다. 덩어리마다 아래 질문에 **예(근거 한 줄) / 아니오(false)**로만 답하고, 점수는 코드가 센다(항목 점수 = 예의 개수 ÷ 그 항목의 질문 수).

| 항목 | id | 질문 |
|:---|:---|:---|
| 목표 | g0 | 왜 만드는지(해결할 문제와 그 이유)가 정해졌다 |
| | g1 | 만들 것을 조건 없이 한 문장으로 말할 수 있다 |
| | g2 | 누가 쓰는지(사용자, 역할)가 정해졌다 |
| | g3 | 핵심 대상과 그 관계(무엇이 무엇을 하는지)가 분명하다 |
| 제약 | c1 | 이번에 하지 않을 것(범위 밖)이 정해졌다 |
| | c2 | 지켜야 할 기술·환경·규칙 조건이 정해졌다 |
| | c3 | 경계 상황(최대·최소, 예외 입력 등)을 어디까지 다룰지 정해졌다 |
| 성공 기준 | s1 | 완성을 확인할 테스트를 바로 쓸 수 있는 기준이 있다 |
| | s2 | 정상 흐름에서 기대하는 결과가 구체적이다 |
| | s3 | 실패·예외 상황에서 기대하는 결과가 정해졌다 |
| 기존 코드 (brownfield만) | x1 | 건드릴 파일·모듈을 코드에서 확인했다 |
| | x2 | 기존 방식(패턴)을 따를지 바꿀지 정해졌다 |
| | x3 | 변경이 다른 기능에 주는 영향을 확인했다 |

- **"예"는 대화나 코드에 근거가 있을 때만.** 근거는 사용자 말이나 파일 경로를 짧게 적는다. 추측이면 false다.
- **아직 한 번도 묻지 않은 항목의 체크는 보내지 않는다.** 안 보낸 체크는 "답 없음"(null)으로 남고, 코드가 그 덩어리에 최저선 +5%p를 붙이고 다음 질문 우선순위에 올린다. 미리 `false`로 보내면 "물어봤는데 아니오"로 세어져서 그 장치가 꺼진다.
- 이번에 물은 항목(`dimension`)의 체크는 이번 답을 반영해 **모두** 답한다. 이번 답 때문에 다른 항목·덩어리의 체크가 바뀌었으면 그것도 함께 보낸다. 보내지 않은 체크는 이전 값이 유지된다.
- 답이 앞서 확정한 내용과 어긋나거나, 질문을 비켜 갔거나, 범위를 늘렸으면 해당 체크를 false로 되돌리고 `events`에 적는다.

#### 기록

사용자 답을 받으면 바로 `record`를 실행한다.

```
IV record --input '{"round":1,"component":"apply","dimension":"goal","question":"<질문>","answer":"<답 또는 정리본>","answer_source":"user","reason":"<왜 물었나>","checks":{"apply":{"g0":false,"g1":"직원이 웹에서 연차를 신청 (R1 답)","g2":"직원 본인만 (R1 답)","g3":false}},"facts":[{"id":"f1","statement":"신청은 직원 본인만","evidence":"R1 답"}],"events":[],"notes":"<세 관점 점검 메모 등>"}'
```

위 예시는 목표(goal)만 물은 1라운드라 `g0~g3`만 보낸다. 제약·성공 기준은 아직 안 물었으니 보내지 않는다.

| 필드 | 뜻 |
|:---|:---|
| `facts` | 새로 확정된 사실 (id, statement, evidence) |
| `dispute` | 뒤집힌 사실 id 목록. 지우지 않는다 |
| `confirm` | 사용자가 원래 사실을 다시 확인한 경우의 id 목록 |
| `supersede` | `[{"old":"f1","new":"f2"}]` 새 사실이 옛 사실을 대신함 (새 사실은 같은 요청의 `facts`에 넣는다) |
| `events` | `[{"type":"충돌\|모순\|회피\|범위 확장","detail":"..."}]` |

같은 라운드 번호를 다른 답으로 다시 보내면 "답 번복"으로 처리되어 그 라운드의 사실이 뒤집힘으로 표시된다.

**최저선.** 코드는 아래를 세서 모호도가 이보다 낮게 나오지 않게 한다: 뒤집힌 채 정리되지 않은 사실 1개당 +10%p, 이 인터뷰의 항목(목표·제약·성공 기준, 기존 코드 고치기면 기존 코드까지) 중 답하지 않은 항목이 있는 덩어리 1개당 +5%p, AI 대리 답 비율 × 5%p. 뒤집힌 사실은 `supersede`나 `confirm`으로 정리하거나, 같은 id로 새 합의를 `facts`에 다시 보내야 최저선이 내려간다.

#### 점수표

`record` 결과의 숫자만 쓴다.

```
**Round {n} 완료**

| 항목 | 점수 | 비중 | 반영 |
|:---|---:|---:|---:|
| {scores[].name} | {score} | {weight} | {weighted} |
| **모호도** | | | **{ambiguity_before}% → {ambiguity}%** |

**덩어리:** {components[].name} {mark} · ...
```

- `clamped_by_floor: true`면 표 아래에 "최저선 {floor}%: {floor_reasons}" 한 줄을 쓴다.
- 모호도가 올랐으면 `events`의 이유를 한 줄로 쓴다.

**언제 멈추나.** 보통 라운드가 끝나면 "계속할까요?"를 묻지 않고 바로 다음 질문으로 간다. 멈추는 건 아래 경우뿐이다.

| 상황 | 할 일 |
|:---|:---|
| `threshold_met: true` | 4. 마무리로 |
| 모호도는 기준 아래인데 `threshold_met: false` | `lagging_components`의 덩어리가 아직 혼자 기준을 못 넘음. 그 덩어리를 더 묻는다 |
| "그만", "취소" | 바로 `IV end --status cancelled`, 지금까지 정한 것을 짧게 정리. 되묻지 않음 |
| "이제 됐어", "그냥 만들어" (3라운드 이후) | 남은 빈 곳(`next.unmet`)을 보여주고 `그대로 스펙 저장` / `몇 개 더 묻기` / `취소` 중 고르게 함. 저장을 고르면 `IV early-exit` 후 4. 마무리로 |
| 같은 말 (3라운드 전) | 무엇이 답답한지 질문 하나로 확인 |
| `hard_cap: true` (30라운드) | 사용자에게 알리고 `IV early-exit` 후 4. 마무리로 |

### 세 관점 점검

`record` 결과에 `milestone_changed`가 있을 때(구간: 시작 >60% → 중간 → 막바지 → 완료 ≤기준값, 어느 방향이든), 그리고 "알아서 해"에 답하기 전에, 혼자서 세 시각으로 다시 본다.

- **삐딱하게:** 사용자가 당연하게 말한 조건이 진짜 필요한 건지, 그냥 익숙해서 붙인 건지.
- **줄여서:** 이 중 절반만 만들어도 쓸모가 있다면 어느 절반인지.
- **바깥에서:** 지금 대화가 기대고 있는데 아직 확인하지 않은 외부 사정(다른 시스템, 규정, 선례)이 있는지.
- 범위가 늘어난 라운드였다면 **구조**도 본다: 누가 무엇을 맡는지, 어디와 연결되는지가 바뀌었는지.

점수표 아래에 "구간: {milestone_changed}" 한 줄과 쓸 만한 발견 2~3줄만 쓴다. 발견은 다음 질문의 선택지나 추천에 녹이고, 다음 `record`의 `notes`에 남긴다. 점검 때문에 질문 수를 늘리지 않는다.

### 4. 마무리

**한 번 더 의심하기.** 점수가 기준을 넘었다고 바로 끝내지 않는다. `IV status`로 확인한다: 모든 덩어리에 목표·제약·성공 기준 체크가 있는가, 뒤집힌 채 남은 사실이 있는가, 확신 낮은 AI 대리 답이 중요한 자리에 있는가. 중요한 게 비었으면 "점수는 기준을 넘었지만 {빈 곳}이 정해지지 않아 조금 더 여쭙겠습니다"라고 말하고 그 질문을 하나 더 한다(새 라운드로 기록). 사소한 건 내가 정하고 스펙의 "내가 대신 정한 것"에 적는다.

**한 문장으로 맞춰 보기.** 덩어리별 결정을 표로 보여주고, 전체를 한 문장으로 요약한다. AskUserQuestion으로 "이 문장대로 만들면 원하시는 결과가 나올까요?"를 묻는다. 선택지: `네, 이대로`, `표현 고치기`, `빠진 게 있음`. 고칠 게 있으면 반영해서 새 라운드로 기록하고 다시 묻는다. 두 번 해도 안 맞으면 질문 루프로 돌아간다.

### 5. 스펙 저장과 인터뷰 종료

`네, 이대로`를 받으면 (이 확인 답은 `record`하지 **않는다**. 저장 조건이 "마지막 라운드 뒤의 사용자 답"을 보기 때문이다. `표현 고치기`로 문장을 고쳤으면 그 답은 라운드로 기록하고 확인을 한 번 더 받는다):

1. `IV status`로 전체 기록(라운드, 체크 근거, 사실, 덩어리)을 읽는다.
2. Write 도구로 `.deep-interview/specs/deep-interview-{주제}.md`를 쓴다. `{주제}`는 짧은 영어 소문자에 하이픈(예: `leave-request`). 훅은 저장 조건(기록된 라운드, 기준 통과 또는 조기 종료, 마지막 라운드 뒤 사용자 확인)만 검사하고 본문은 읽지 않는다. 막히면 그 이유를 해결한다.
3. 고정 항목은 `scope`에서 확정한 ID를 **모두** `- \`ID\` — 설명` 줄로 넣는다. 결과 줄은 `기준 통과`와 `기준 미달로 조기 종료` 중 **하나만** 적는다. deep-build가 인터뷰 기록과 대조해서, 빠진 고정 항목이 있거나 결과 줄이 양식 그대로면 시작을 거부한다.
4. `IV end --spec .deep-interview/specs/deep-interview-{주제}.md`로 인터뷰를 끝낸다. 차단이 풀린다.

```markdown
# {제목} — 딥 인터뷰 스펙

## 한눈에 보기
- 문제(왜): {지금 무엇이 불편한지, 이걸 만들면 무엇이 나아지는지}
- 한 문장 요약: {문장}
- 최종 모호도: {점수}% (기준값 {기준값}, {출처})
- 라운드: {개수}
- 종류: 새로 만들기 | 기존 코드 고치기
- 결과: 기준 통과 | 기준 미달로 조기 종료
- 날짜: {날짜}
- 다시 의심해서 질문을 더 한 횟수: {n}
- 세 관점 점검: {횟수와 구간}
- 내가 대신 정한 라운드: {목록 또는 없음}
- 긴 답을 정리한 라운드: {목록 또는 없음}

## 무엇을 만드나
{한 문단 설명}

| 덩어리 | 상태 | 설명 | 어디까지 정했나 / 미룬 이유 |
|:---|:---:|:---|:---|

**고정 항목**
- `{종류:이름}` — {설명}

## 경계
**지킬 조건**
- {조건}

**하지 않을 것**
- {범위 밖}

**나중으로 미룬 것**
- {미룬 것과 이유}

## 다 됐다는 기준
- [ ] {테스트로 확인할 수 있는 기준}

## 남은 질문
{인터뷰에서 정하지 못했지만 만들기 전이나 만드는 중에 답이 필요한 질문. 누가 답해야 하는지와 함께. 없으면 "없음"}
- [ ] {질문} — {누가 / 언제까지}

## 어떻게 정해졌나

**체크리스트 결과**
| 덩어리 | 체크 | 결과 | 근거 |

**확정된 사실**
| 번호 | 내용 | 라운드 | 근거 | 상태 |

**점수 변화**
| 라운드 | 덩어리 | 항목 | 계산값 | 최저선 | 모호도 |

**점수를 올린 사건**
| 라운드 | 무슨 일 | 덩어리 | 변화 |

**세 관점 점검**
| 라운드 | 구간 | 관점 | 다음 질문에 반영한 것 |

**꺼내서 확인한 전제**
| 전제 | 어떻게 확인했나 | 결론 |

**내가 대신 정한 것**
- {무엇을, 왜}

## 코드와 개념

**코드에서 확인한 것** (고치는 일일 때)
- {파일 경로·함수와 확인 내용}

**개념 목록**
| 대상 | 성격 | 속성 | 관계 |

## 문답 기록
<details>
<summary>{n} 라운드</summary>

### Round 1
- 질문: {질문}
- 답: {답}
- 모호도: {점수}%
</details>
```

저장하면 아래를 보여준다.
- 스펙 경로
- 최종 모호도와 라운드 수
- 한 문장 요약

### 6. 다음 단계로 넘기기

`end`가 끝난 뒤(차단이 풀린 뒤)에 한다.

| 스펙 결과 | 할 일 |
|:---|:---|
| 기준 통과 | Skill 도구로 deep-build를 부른다. 인자는 스펙 경로. 예: `Skill(skill: "deep-workflow:deep-build", args: ".deep-interview/specs/deep-interview-leave-request.md")`. 스킬 목록에 `deep-workflow:deep-build`가 없고 `deep-build`만 있으면 그 이름으로 |
| 조기 종료 (기준 미달) | 스펙의 "남은 질문"과 미달 사실을 보여주고 AskUserQuestion으로 "그래도 설계·계획으로 넘어갈까요?"를 **한 번** 묻는다. 선택지: `넘어가기`, `여기서 멈추기`. 넘어가면 인자에 ` --force`를 붙여 부르고, 멈추면 끝 |
| 취소 (`--status cancelled`) | 스펙이 없으므로 넘기지 않는다 |

`deep-build`는 같은 플러그인(deep-workflow)에 들어 있다. 어떤 이유로든 부를 수 없으면 스펙 경로와 `/deep-build <경로>` 명령을 보여주고 멈춘다. 딥 인터뷰는 단독으로도 쓸 수 있어야 한다.

## 이어하기

세션이 끊겼다가 같은 세션으로 돌아오면 `IV status`를 실행한다. `active: true`면 `next`부터 이어간다. `answers_recorded`가 사용자 답을 받았는데도 늘지 않으면 플러그인 훅이 동작하지 않는 것이니 사용자에게 알린다.

## 끝내기 전 확인

- [ ] `start` 결과의 `marker`를 첫 줄에 보여줬다
- [ ] 사용자 확인 뒤 `scope`를 실행했다
- [ ] 질문은 매번 하나였고, 추천을 첫 번째에 뒀다
- [ ] 매 라운드 `record`를 실행했고, 화면의 숫자는 그 결과에서 가져왔다
- [ ] 체크 "예"마다 근거를 적었다
- [ ] 구간이 바뀔 때 세 관점 점검을 했다
- [ ] 한 번 더 의심하기와 한 문장 맞춰 보기를 거쳤다
- [ ] 스펙을 저장했고 고정 항목이 다 들어 있다
- [ ] `end`로 인터뷰를 끝냈다 (그만둘 때는 `--status cancelled`)
- [ ] 기준 통과면 `deep-build`로 넘겼고, 조기 종료면 한 번 물었다
